# پرداخت با تتر (USDT)

یه راه پرداخت دوم کنار کارت‌به‌کارت: مشتری روی فاکتور «💎 پرداخت با USDT
(TRC20)» رو می‌زنه، یه مبلغ دقیق می‌گیره، واریز می‌کنه و **لایسنس خودکار
صادر می‌شه** -- بدون رسید، بدون OCR، بدون منتظرِ ادمین موندن.

پیش‌فرض **خاموشه**. تا `crypto.enabled` رو روشن نکنی و آدرس ننویسی، هیچ
دکمه‌ای به مشتری نشون داده نمی‌شه و جریان کارتی دقیقاً مثل قبله.

---

## اول: ربات هیچ‌وقت کلید خصوصی نداره

ربات فقط **آدرس عمومیِ** کیف‌پولِ تو رو *تماشا می‌کنه* (فقط‌خواندنی):
هر ۳۰ ثانیه از یه API عمومی می‌پرسه «چه تراکنشی به این آدرس رسیده؟».
هیچ‌چیزی امضا یا ارسال نمی‌شه.

معنیش این‌ه که اگه دیتابیس، کانفیگ یا سرور ربات لو بره، **به پولِ تو
دسترسی پیدا نمی‌شه** -- بدترین حالت اینه که کسی آدرس دریافتت رو ببینه، که
ذاتاً عمومیه. کلید خصوصی کیف‌پول همیشه دست خودته، جایی که ربات بهش
نمی‌رسه.

نتیجه‌ی مهمِ دیگه: اگه خودت آدرس رو اشتباه بنویسی پول می‌ره به کیف‌پولِ
یه نفر دیگه. به همین دلیل برای ترون چک‌سامِ آدرس موقع بالا اومدن
راستی‌آزمایی می‌شه (آدرسِ غلط تایپی رد می‌شه و دکمه نمی‌آد).

## راه‌اندازی

توی `data/licensing/config.json` (بعد از `python license_server.py --init`
بخش `crypto` خودش توی فایل نمونه هست):

```json
{
  "crypto": {
    "enabled": true,
    "network": "trc20",
    "address": "T...آدرس دریافت خودت...",
    "trongrid_api_key": "",
    "expiry_minutes": 30,
    "min_confirmations": 1
  }
}
```

| کلید | پیش‌فرض | توضیح |
|---|---|---|
| `crypto.enabled` | `false` | کلید اصلی. خاموش = هیچ اثری توی ربات نیست |
| `crypto.network` | `"trc20"` | `trc20` (USDT روی ترون) یا `bep20` (USDT روی BSC) |
| `crypto.address` | `""` | آدرس دریافتِ خودت. خالی = دکمه نمی‌آد |
| `crypto.trongrid_api_key` | `""` | اختیاری. بدونش هم کار می‌کنه؛ با کلید سقفِ درخواستِ TronGrid بالاتره |
| `crypto.explorer_api_key` | `""` | فقط `bep20`: کلید رایگان Etherscan (API نسخه‌ی ۲ که BSC رو هم داره) |
| `crypto.expiry_minutes` | `30` | مهلتِ پرداخت بعد از ساختِ فاکتور (حداقل ۵) |
| `crypto.min_confirmations` | `1` | ترون: `0` = همون لحظه‌ای که دیده شد، `۱` و بیشتر = فقط تراکنشِ قطعی‌شده. BSC: تعداد تأییدِ بلاک |

آدرس و کلیدها رو می‌تونی با متغیر محیطی هم بدی (امن‌تر روی سرور):

```bash
export LICENSING_CRYPTO_ADDRESS=T...
export LICENSING_TRONGRID_API_KEY=...
export LICENSING_EXPLORER_API_KEY=...
```

بعدش:

```bash
python license_server.py --check    # «پرداخت با تتر: فعال (USDT (TRC20))»
```

اگه روشنه ولی ناقصه (آدرس خالی، آدرس نامعتبر، شبکه‌ی ناشناس) `--check`
همون‌جا مشکل رو می‌گه. ادمین هم توی ربات، از «💎 پرداخت‌های کریپتو»،
دلیلش رو می‌بینه. تغییر کانفیگ با `/reload` یا ری‌استارت اعمال می‌شه.

**فروشنده‌ی فقط‌کریپتو:** اگه `card_number` نداری ولی کریپتو فعاله، ربات
بدون شماره کارت هم بالا میاد و دکمه‌ی کارت از فاکتور حذف می‌شه.

### پروکسی

درخواست‌های شبکه (TronGrid / Etherscan) از همون مسیر Cloudflare KV می‌رن:
اول مستقیم، اگه نشد با `proxy_url` ربات فروش (یا متغیر `LICENSING_PROXY_URL`).
لازم نیست چیز جدیدی تنظیم کنی. جزئیات پروکسی: [LICENSING.md](LICENSING.md).

## جریان

```
فاکتور
  │ «💎 پرداخت با USDT (TRC20)»
  ▼
سفارش ساخته می‌شه (وضعیت: awaiting_crypto) + یه مبلغِ یکتا
  │
  ▼
پیام مشتری:
    مبلغ دقیق  ← داخل <code>، با یه لمس کپی می‌شه
    آدرس       ← داخل <code>
    مهلت       ← «تا ۱۴:۲۵ (۲۸ دقیقه‌ی دیگه)»
    [🔄 فرستادم / همین الان چک کن]  [❌ انصراف]
  │
  │   هر ۳۰ ثانیه (فقط وقتی پرداختِ در انتظار هست) + هر بار که
  │   مشتری دکمه‌ی «چک کن» رو بزنه:
  ▼
تطبیق با تراکنش‌های ورودیِ آدرس
  │ جور شد
  ▼
هش تراکنش ثبت می‌شه (دوباره قابل استفاده نیست)
  ▼
approval.issue_order_license(...)   ← همون مسیرِ دکمه‌ی «✅ تأیید» ادمین
  ▼
به مشتری: «پرداخت دریافت شد» + لایسنس + دکمه‌ی راه‌اندازی ربات
به ادمین‌ها: «💎 پرداخت تتر دریافت شد، سفارش #۴۲، تراکنش …، لایسنس …»
```

همین فاکتور از صفحه‌ی پرداخت کارتی هم در دسترسه: کسی که اول «پرداخت
می‌کنم» (کارت) رو زده، همون‌جا دکمه‌ی «💎 پرداخت با USDT» رو هم می‌بینه و
روی **همون سفارش** روش رو عوض می‌کنه.

تأیید خودکار از **همون تابعی** می‌گذره که ادمین صداش می‌زنه
(`licensing/telegram/sales/approval.py::issue_order_license`): ساخت یا
تمدیدِ لایسنس، مصرف کد تخفیف، ری‌استارت ربات‌ها بعد از تمدید، پیام به
مشتری. تأییدِ دستی و خودکار هیچ‌وقت از هم جدا نمی‌شن.

## مبلغ یکتا و قواعد تطبیق

روی بلاک‌چین فرستنده «شماره‌ی سفارش» نمی‌نویسه؛ از هر تراکنش فقط مقصد،
مبلغ، زمان و هش رو داریم. پس **مبلغ همون شناسه‌ی سفارشه**:

```
مبلغ = قیمت فاکتور (دلار) + آفست تصادفی بین ۰٫۰۰۰۱ تا ۰٫۰۹۹۹ تتر
مثال: فاکتور ۱۲٫۵ دلار  →  ۱۲٫۵۰۳۴ USDT
```

آفست بین پرداخت‌های **در انتظار** یکتاست (۹۹۹ مبلغِ ممکن برای هر قیمت؛
هم توی کد چک می‌شه، هم یه ایندکس یکتا توی دیتابیس تضمینش می‌کنه). اگه
همه‌ی ۹۹۹ تا درگیر باشن، مشتری پیام «چند دقیقه‌ی دیگه امتحان کن یا با
کارت بده» می‌گیره و سفارشِ یتیم ساخته نمی‌شه. مبلغ به «میکرو‌تتر» (عدد
صحیح) ذخیره می‌شه تا هیچ خطای اعشاری توی مقایسه نباشه. دکمه‌ی دوباره‌زدن
همون فاکتور باز رو نشون می‌ده و مبلغ تازه نمی‌سازه.

یه تراکنش فقط وقتی پرداخت حساب می‌شه که **همه‌ی این‌ها** درست باشن:

| شرط | توضیح |
|---|---|
| توکن | USDT واقعی (آدرس قرارداد چک می‌شه، نه فقط اسم توکن) |
| مقصد | دقیقاً آدرس دریافت تو |
| مبلغ | **دقیقاً** برابر مبلغ فاکتور؛ نه کمتر، نه بیشتر |
| زمان | زمانِ تراکنش توی بازه‌ی [ساخت فاکتور، انقضا] |
| تأیید | حداقل `min_confirmations` |
| هش | قبلاً برای پرداخت دیگه‌ای ثبت نشده |

شرطِ آخر با ایندکس یکتای `(network, tx_hash)` توی دیتابیس اجرا می‌شه، نه
فقط با یه `if`: حتی دو بررسیِ هم‌زمان (حلقه‌ی پس‌زمینه و دکمه‌ی مشتری)
نمی‌تونن یه تراکنش رو دو بار خرج کنن.

## انقضا

هر فاکتور `expiry_minutes` (پیش‌فرض ۳۰) اعتبار داره. بعدش:

  * پرداخت `expired` می‌شه و مبلغش آزاد؛ سفارش هم `expired` می‌شه.
  * مشتری پیام می‌گیره: «اگه قبلاً واریز کردی، هش تراکنش رو برای پشتیبانی
    بفرست».
  * تراکنشی که **زمانش** بعد از انقضاست هیچ‌وقت تطبیق نمی‌خوره.

یه مهلت ارفاقِ ۲ دقیقه‌ای هم هست: پرداختی که *توی مهلت* انجام شده ولی
لحظه‌ی آخر دیده شده، جا نمی‌مونه (منقضی‌کردن همیشه *بعد از* تطبیق انجام
می‌شه). لغو سفارش هم فاکتور رو می‌بنده.

## پنل ادمین

**پنل ادمین → 💎 پرداخت‌های کریپتو**:

  * وضعیتِ پیکربندی (شبکه و آدرس، یا دلیل غیرفعال‌بودن)
  * پرداخت‌های منتظر: سفارش، مبلغ، چند دقیقه مونده، کاربر -- با یه دکمه
    برای هر کدوم که سفارش رو باز می‌کنه (تأییدِ دستی)
  * آخرین دریافتی‌ها: مبلغ، تاریخ، لینک تراکنش توی اکسپلورر. ردیفِ ⚠️ یعنی
    پول رسید ولی تأیید خودکار نشد
  * «🔄 همین الان چک کن» (یه دور بررسی)

### وقتی تأیید خودکار نشد

اگه پول رسیده ولی صدور لایسنس خطا داد (نادر): پرداخت با وضعیت
`approval_failed` می‌مونه، خطا توی لاگ می‌آد، و به ادمین‌ها پیامِ «⚠️
تأیید خودکار نشد» می‌رسه. از همون صفحه سفارش رو باز کن و «✅ تأیید» بزن.
مشتری به خاطر خطای ما پولش گم نمی‌شه و دوباره هم پرداخت نمی‌کنه.

### مبلغ اشتباه یا دیررس

**مبلغِ کمتر یا بیشتر، عمداً خودکار تأیید نمی‌شه.** چون ربات نمی‌تونه
بفهمه این تراکنش مالِ کدوم سفارشه، یا پولِ کامل رسیده یا نه. مشتری
معمولاً با هش تراکنش به پشتیبانی پیام می‌ده؛ تو هم تراکنش رو توی اکسپلورر
می‌بینی و اگه درست بود سفارش رو دستی تأیید می‌کنی. تأییدِ دستی فاکتورِ
باز رو می‌بنده تا بعداً با یه تراکنشِ دیررس دوباره تأیید نشه.

شایع‌ترین علتِ مبلغ اشتباه: **صرافی‌ها کارمزد برداشت رو از خودِ مبلغ کم
می‌کنن.** بهش توی پیام مشتری هشدار داده شده («طوری بفرست که مقصد دقیقاً
همین مبلغ رو دریافت کنه») ولی بعضی مشتری‌ها می‌خونن و بعضی نه.

## شبکه‌ها

### TRC20 (پیش‌فرض، لازم)

```
GET https://api.trongrid.io/v1/accounts/{address}/transactions/trc20
    ?only_to=true
    &contract_address=TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t    (USDT)
    &min_timestamp=...&limit=200&order_by=block_timestamp,desc
    [&only_confirmed=true]      وقتی min_confirmations >= 1
هدر اختیاری:  TRON-PRO-API-KEY: <trongrid_api_key>
```

بدون کلید API هم کار می‌کنه؛ ربات توی حالت عادی هر ۳۰ ثانیه *یک*
درخواست می‌زنه، و فقط وقتی پرداختِ منتظر هست.

### BEP20 (USDT روی BSC؛ آزمایشی)

از API چندزنجیره‌ای Etherscan (`chainid=56`) می‌خونه و کلید رایگان
(`crypto.explorer_api_key`) می‌خواد. مبلغ روی BSC با ۱۸ رقم اعشاره؛
تراکنشی که رقم‌های اضافه‌تر از شش رقم داشته باشه «مبلغ دقیق» حساب نمی‌شه.
این شبکه فقط با داده‌ی ساختگی تست شده؛ قبل از فروش واقعی یه تراکنش کوچیک
خودت امتحان کن.

### اضافه‌کردن شبکه‌ی جدید

توی `licensing/crypto_pay.py` یه کلاس مثل `_TronNetwork` بنویس (`code`،
`label`، `valid_address`، `fetch_incoming`، `tx_url`) و توی `NETWORKS`
ثبتش کن. بقیه‌ی سیستم (مبلغ یکتا، تطبیق، انقضا، تأیید، پنل) دست‌نخورده
کار می‌کنه.

## داده‌ها

جدول `crypto_payments` (توی `licensing/db.py`؛ برای دیتابیس‌های قدیمی با
همون `CREATE TABLE IF NOT EXISTS` موقع بالا اومدن ساخته می‌شه و به
جدول‌های دیگه دست نمی‌زنه):

| ستون | توضیح |
|---|---|
| `order_id`، `user_id` | سفارش و مشتری |
| `network`، `address` | شبکه و آدرسِ زمانِ ساخت فاکتور (عوض‌کردنِ کانفیگ فاکتورهای باز رو خراب نمی‌کنه) |
| `amount_micro` | مبلغ به میکروتتر (عدد صحیح) |
| `status` | `pending` ← `paid` / `expired` / `cancelled` / `manual` / `approval_failed` |
| `tx_hash` | هش تراکنش پرداخت؛ یکتا به ازای شبکه |
| `created_at`، `expires_at`، `paid_at` | زمان‌ها (ثانیه) |

وضعیت سفارش هنگام انتظار `awaiting_crypto` است. رویدادها توی جدول
`events` ثبت می‌شن: `crypto_invoice`، `crypto_paid`.

## محدودیت‌ها و نکته‌ها

  * **ساعت سرور باید درست باشه** (NTP). تطبیق زمانی از مقایسه‌ی ساعت سرور
    با زمان بلاک استفاده می‌کنه.
  * هر دور فقط ۲۰۰ تراکنشِ آخرِ آدرس رو می‌بینه. برای حجم عادی یه
    فروشگاه کافیه؛ اگه روزی آدرس‌ت هر ۳۰ ثانیه بیشتر از ۲۰۰ واریز می‌گیره،
    یه آدرس جدا برای ربات بگیر.
  * همه‌ی پرداخت‌های در انتظار یه آدرس دارن؛ تفکیک با مبلغه، نه آدرس.
  * خطای شبکه (TronGrid قطع، محدودیت درخواست) پرداخت رو خراب نمی‌کنه: همون
    دور رد می‌شه و ۳۰ ثانیه بعد دوباره امتحان می‌شه. دکمه‌ی مشتری در این
    حالت می‌گه «سرویس جواب نداد»، بدون متنِ فنیِ خطا.
  * پرداخت با تتر هیچ نرخ تومانی نمی‌خواد و به `pricing.refresh_rate`
    وابسته نیست؛ مبلغ مستقیم از قیمت دلاریِ سفارش (بعد از کد تخفیف) می‌آد.
