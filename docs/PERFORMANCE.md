# سرعت ربات و کم‌کردن درخواست‌ها

دو هدفی که با هم در تضادن: **سریع بودن** (کاربر منتظر نمونه) و **کم‌ردپا
بودن** (سرویس ما رو scraper حساب نکنه). راه‌حل این پروژه: این دو تا رو از
هم جدا کن و برای هر کدوم قاعده‌ی خودش رو بذار.

---

## مسیر تعاملی در برابر مسیر دسته‌ای

`_opts(interactive=True)` یعنی «کاربر همین الان منتظر این درخواسته».

| | تعاملی | دسته‌ای / پس‌زمینه |
|---|---|---|
| کِی | آیتم اول یه سرچ، لینک تکی، لیست کانال | رشد صف (`n`)، resolve موازی، `search_batch` |
| `sleep_interval_requests` | ۰ | ۱ ثانیه |

چرا این بزرگ‌ترین بُرد سرعت بود: `sleep_interval_requests=1` یه ثانیه بین
*هر* درخواست داخلی یه استخراج مکث می‌ذاره، و یه استخراج یوتیوب چند درخواست
داخلی داره. یعنی چند ثانیه تأخیر روی همون آیتمی که کاربر بهش نگاه می‌کنه —
در حالی که حجم واقعی درخواست‌ها توی کارهای دسته‌ایه، نه توی اون یه آیتم.
پس مکث از جایی که به چشم می‌آد برداشته شد و جایی که مهمه موند.

## چه چیزهایی درخواست را حذف می‌کنند

| لایه | اثر |
|---|---|
| `_search_cache` (۳۰ دقیقه) | سرچ تکراری = صفر درخواست |
| `_playlist_stub_cache` (۱ ساعت) | پخش دوباره‌ی یه پلی‌لیست فقط آیتم اول رو resolve می‌کنه |
| `_search_stub_cache` (۳۰ دقیقه) | رشد صف با `n` تا وقتی از کش جواب بده، صفر درخواست |
| `_description_cache` | `di` از چیزی که موقع resolve گرفته شده می‌خونه، نه یه درخواست نو |
| `_channel_cache` (۳۰ دقیقه) | لیست کانال/پلی‌لیست تکراری = صفر درخواست |
| YouTube Data API (اگه کلید بدی) | سرچ متنی با یه درخواست سبک، به‌جای scrape سنگین |
| `SEARCH_STUB_FETCH_SIZE=40` | یه بار ۴۰ نتیجه، به‌جای چند سرچ با count بزرگ‌شونده |
| `ytdl=no` روی mpv | mpv دیگه yt-dlp خودش رو spawn نمی‌کنه |
| `md` (مستند) | آدرس مستقیم ساخته می‌شه؛ **صفر** درخواست قبل از mpv |

### `ytdl=no` چرا مهمه

همه‌ی لینک‌هایی که به mpv داده می‌شن از قبل resolve شدن. پس هوک ytdl خودِ
mpv فقط وقتی فعال می‌شد که چیزی اشتباه رفته باشه — و اون‌موقع بدترین کار رو
می‌کرد: یه پروسه‌ی yt-dlp جدا که **پروکسی و کوکی ما رو نداره**، یعنی یه
درخواست لخت به یوتیوب از همون IP. دقیقاً الگویی که «Sign in to confirm
you're not a bot» می‌سازه.

اگه روزی لینکی داشتی که واقعاً بهش نیاز داشت:

```json
"player": { "allow_mpv_ytdl": true }
```

## باگ‌هایی که موقع بهینه‌سازی پیدا شدند

**استخر yt-dlp تنظیمات جدید رو نادیده می‌گرفت.** نمونه با اولین `opts`
ساخته می‌شد و بعدش همیشه همون برمی‌گشت. یعنی `proxy` و `ck` روی resolve
تک‌تک آیتم‌ها **هیچ اثری نداشتن** — پروکسی فقط روی سرچ سطح‌بالا اعمال
می‌شد. حالا کلید کش شامل اثرانگشت خود تنظیماته.

**همون نمونه بین چند ترد مشترک بود.** `_resolve_entries_parallel` تا ۴ ترد
موازی راه می‌اندازه و همه یه `YoutubeDL` مشترک می‌گرفتن، در حالی که حالت
داخلی قابل‌تغییر داره و برای استفاده‌ی هم‌زمان ساخته نشده. حالا نمونه‌ها
thread-local ان.

**پروب زنده‌بودن گران و بی‌معنی.** هر بار `prepare_filename({"id":"test"})`
صدا زده می‌شد که کل ماشین قالب‌بندی اسم فایل yt-dlp رو اجرا می‌کنه و
درباره‌ی سالم‌بودن نمونه چیزی نمی‌گه. حذف شد.

## حلقه‌ی اصلی

از قبل بهینه بود و دست نخورد؛ برای مرجع:

- تنها نقطه‌ی انتظار `handle_messages(250ms)` است که روی صف رویداد SDK
  بلاک می‌شه — پیام که بیاد فوراً بیدار می‌شیم، نباشه عملاً صفر CPU.
- کارهای دوره‌ای فاصله‌ی مشخص دارن (وضعیت پلیر ۰.۵s، کانال خالی ۲s،
  کانفیگ مشترک ۵s)، نه هر دور.
- `vid=no` یعنی ترک ویدیو اصلاً باز نمی‌شه — برای استریم تصویری، یه هسته
  CPU که بی‌فایده صرف دیکود می‌شد آزاد می‌شه.
- استخر ترد مشترک (سقف ۴) به‌جای `ThreadPoolExecutor` تازه برای هر سرچ.

## تست سلامت راه‌اندازی

بیشتر خرابی‌های این ربات **ساکت**ن: بالا میاد، توی کانال دیده می‌شه، ولی
صدا هیچ‌جا نمی‌ره. موقع استارت این‌ها واقعاً امتحان می‌شن:

- دستگاه خروجی **باز می‌شه** و یه تُن ۰.۳ ثانیه‌ای (تولید داخلی mpv، بدون
  شبکه) پخش می‌شه
- دستگاه ورودی واقعاً `initSoundInputDevice` می‌شه
- لاین صدا روی سیستم زنده هست؟ (روی لینوکس بعد از ریبوت همین از بین می‌ره)
- ffmpeg اجرا می‌شه، سرویس‌ها و دستورها لود شدن، زبان، فضای دیسک، دسترسی
  نوشتن، وضعیت لایسنس، سن فایل کوکی

کل تست حدود **۰.۳ ثانیه** طول می‌کشه (بدون تُن) و **هیچ‌وقت جلوی استارت رو
نمی‌گیره** — فقط گزارش می‌ده.

```
dg              # فقط مشکل‌ها، از داخل تیم‌تاک
dg all          # همه‌ی نتایج
dg boot         # گزارش لحظه‌ی راه‌اندازی
python manage.py selftest
```

خاموش‌کردن تُن (اگه خروجی اسپیکر واقعیه و نمی‌خوای بیپ بشنوی):

```json
"selftest": { "enabled": true, "audio_tone": false }
```

## چیزی که عمداً انجام *نشد*

**کش دیسکی برای لینک استریم.** لینک‌های googlevideo چند ساعت بعد منقضی
می‌شن، پس کش کردنشون بین ری‌استارت‌ها یعنی پخشِ خراب. فقط شناسه/عنوان
(stub) ارزش کش‌شدن دارن و اون‌ها توی حافظه کش می‌شن.

**پایین‌آوردن `retries` به صفر.** سریع‌تر fail می‌کرد، ولی روی شبکه‌ی
ناپایدار (که کاربر اصلی این ربات داره) یعنی خطای بیشتر، نه سرعت بیشتر.

## هزینه‌ی هر پروسه‌ی ربات (مقیاس هزاران ربات روی یه سرور)

هدف: ربات بیکار تا حد ممکن ارزون باشه، چون هر مگابایت × هزار پروسه = گیگابایت.

### اندازه‌گیری (ویندوز، پایتون ۳.۱۲، `tools/loadtest.py spawn -n 8`)

| | قبل | بعد |
|---|---|---|
| RSS هر ربات بیکار (بعد از import کامل ربات) | ۴۶٫۴ MB | **۲۰٫۵ MB** |
| مجموع ۸ پروسه | ۳۷۱ MB | **۱۶۴ MB** |
| زمان import ربات (تک‌پروسه) | ۱٫۳ s | **۰٫۳ s** |
| CPU بیکار | ~۰٪ | ~۰٪ |
| thread | ۳ | ۳ |

برای ۱۰٬۰۰۰ ربات: حدود ۲۶ GB رم کمتر فقط از همین یه تغییر.

### چی عوض شد

- `core/ytdlp_lazy.py`: `yt_dlp` (حدود ۱ ثانیه و ۳۰ MB: همه‌ی extractorها،
  Cryptodome، websockets، requests) دیگه موقع بالا اومدن import نمی‌شه؛
  اولین resolve/پخش واقعی import رو انجام می‌ده. همه‌ی جاهایی که قبلاً
  `from yt_dlp import ...` سطح ماژول داشتن از این ماژول رد می‌شن، پس
  رفتارشون عوض نشده.
- `instagrapi` (با pydantic/PIL) فقط وقتی دستور اینستاگرام اجرا بشه لود
  می‌شه؛ PIL/playwright/STT از قبل داخل تابع import می‌شدن.
- حلقه‌ی اصلی، scheduler و صف retry از قبل بدون busy-loop بودن (بخش بالا)؛
  کش‌ها هم سقف دارن (تاریخچه ۵۰ ورودی، کش سرچ/کانال TTL دارن).

### مانیتورینگ

- دستور ادمین `res` (نقش `admin_bot`): رم، میانگین CPU از شروع پروسه،
  تعداد thread و مدت اجرا. توی `ah` هم دیده می‌شه.
- `python tools/loadtest.py spawn -n N -d ثانیه [--root پوشه]`: N ربات
  «بیکار» (import کامل + انتظار) می‌سازه و RSS/CPU/thread/زمان import رو
  گزارش می‌ده؛ `--root` برای مقایسه‌ی قبل/بعد روی یه checkout دیگه.
- `python tools/loadtest.py attach [-m bot.py]`: پروسه‌های ربات در حال
  اجرا رو می‌سنجه. شبیه‌ساز TeamTalk/mpv رو شامل نمی‌شه؛ هزینه‌ی پایه‌ی
  ربات رو نشون می‌ده که در تعداد ضرب می‌شه. (psutil لازمه.)

### قاعده برای کد جدید

کتابخونه‌ی سنگین (بیش از ~۱۰ MB یا ~۱۰۰ms import) نباید سطح ماژول import
بشه؛ داخل تابعی که لازمش داره import کن، یا اگه چند جا لازمه یه shim مثل
`ytdlp_lazy` بذار. تست `LazyYtdlp` توی `tests/test_resource_stats.py`
جلوی برگشتنش رو می‌گیره.

## پیدا کردن لینک تا شروع پخش (شامل لایو)

هدف: کوتاه‌کردن فاصله‌ی «کاربر لینک/سرچ داد» تا «صدا واقعاً شروع شد»،
مخصوصاً لایوهای HLS (یوتیوب و بقیه) که چندین درخواست پشت‌سرهم دارن.

### چی عوض شد

- **استفاده‌ی دوباره از YoutubeDL بین resolveها** (`core/proxy_retry.py`).
  `extract_with_fallback` (مسیرِ داغِ هر p/u/پیستِ لینک) قبلاً هر بار یه
  YoutubeDL کاملاً تازه می‌ساخت (ثبتِ extractorها، cookiejar، سشنِ HTTP) و
  دورش می‌انداخت. حالا از همون pool ای رد می‌شه که `extract_pooled` قبلاً
  داشت، پس resolveهای پشت‌سرهمِ یه ترد از یه نمونه‌ی گرم (و کانکشن HTTP
  keep-alive‌ش) استفاده می‌کنن. اندازه‌گیریِ کنترل‌شده (۳ resolve پشت‌سرهمِ
  یه لینکِ یوتیوب، از پشتِ همین پروکسی): **۱۲٫۳۷ ثانیه -> ۸٫۵۸ ثانیه**.
- **حذفِ یه دانلودِ اضافه‌ی کاملِ m3u8 برای لایو** (`bot.py::_expand_item`).
  هر پخش (نه فقط لایو) از `resolve_playlist` رد می‌شد که اگه لینک به
  `.m3u8`/`.m3u` ختم بشه کاملِ بدنه‌ش رو دانلود می‌کنه تا مطمئن بشه مانیفستِ
  واقعیه نه یه فایلِ متنیِ لیستِ‌آهنگ. لینکِ فرمتِ HLS ای که خودِ yt-dlp
  انتخاب کرده (لایوِ یوتیوب و مشابه) همیشه به `.../index.m3u8` ختم می‌شه،
  یعنی این فچ برای *هر* پخشِ لایو دوبار انجام می‌شد: یه بار داخلِ خودِ
  استخراجِ yt-dlp، یه بار دیگه همین‌جا بی‌دلیل -- حدود **۲٫۶ ثانیه** تلفِ
  هر پخشِ لایو از پشتِ پروکسی. نتیجه‌ای که از yt-dlp میاد از قبل قطعی
  می‌گه استریمِ واقعیه (خودش از `formats` انتخابش کرده)، پس دیگه لازم
  نیست حدس بزنیم؛ چنین نتیجه‌ای با `verified_media: True` علامت می‌خوره
  و `_expand_item` با دیدنش کاملاً از این فچ صرف‌نظر می‌کنه. لینک‌هایی که
  از yt-dlp رد نشدن (پیستِ خام که فقط با پسوند تشخیص داده شده، آخرین
  راه‌حلِ «لینکِ خام به mpv»، کانال‌های IPTV) رفتارِ قبلی‌شون دست‌نخورده‌ست.

### اندازه‌گیریِ end-to-end واقعی (یک لایوِ یوتیوبِ واقعی، از پشتِ پروکسیِ محلی)

| مرحله | زمان (نمونه) |
|---|---|
| resolve (yt-dlp، از پشتِ پروکسی) | ۱۹٫۷ s |
| باز شدنِ mpv تا شروعِ واقعیِ پخش | ۷٫۷ s |
| **جمع** | **۲۷٫۵ s** |

نکته‌ی مهم: بخشِ resolve کاملاً وابسته به تأخیرِ خودِ پروکسیه (بینِ
دو اجرا از ۷ تا ۲۰ ثانیه دیده شد) و کدِ ما کنترلی روش نداره؛ بهبودهای
بالا (pool + حذفِ فچِ اضافه) دقیقاً همون بخش‌هایی‌ان که کدِ خودمون
مسئولشونه، و اندازه‌گیریِ کنترل‌شده‌شون (نه end-to-endِ پرنویز) عددِ
قابل‌اتکاتریه.

### تست‌های دیگر

بقیه‌ی منابعِ لایو (IPTV با core/iptv.py، m3u8ِ عمومی) از همون مسیرِ
`_expand_item` رد نمی‌شن مگه از یه سرویسِ yt-dlp-محور بیان، پس رفتارشون
دست‌نخورده می‌مونه -- تست‌های `tests/test_expand_item_verified_media.py`
همین مرزبندی رو قفل می‌کنه.
